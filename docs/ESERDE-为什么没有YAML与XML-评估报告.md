# Eserde 格式扩展评估：为什么没有 YAML / XML，值不值得加

> 结论先行：**不值得把完整 YAML / XML 内置进 eserde**。
> 准确的说法也不是"只支持 JSON"——库里现有 **JSON + CBOR** 两个格式，架构还刻意把"加一个新格式"的成本压到几十行（见 [ESERDE-使用手册.md](libs/ESERDE-使用手册.md) 3.8 的 TOML-ish 示例）。
> YAML / XML 没进库，不是架构拦着，而是"完整解析器的工程量 vs 嵌入式场景的收益"这笔账不划算。真有需求时按场景选轻量替代（§5），架构零改动。
>
> 评估日期：2026-10-03 · 结论性质：建议（不涉及代码改动）

---

## 1. 先纠正前提：并不是"只支持 JSON"

| 文件 | 行数（含注释） | 职责 |
|---|---|---|
| `eserde/serde.hpp` | 222 | 基座：能力标签查询 + schema 查询 + 按索引访问成员（与具体格式无关） |
| `eserde/traits.hpp` | 133 | 取值形状判定 + 取值搬运助手（**JSON / CBOR 共用**，加第二格式不用抄判定） |
| `eserde/json.hpp` | 925 | JSON 文本读写（RFC 8259 语义） |
| `eserde/cbor.hpp` | 785 | CBOR 二进制读写（RFC 8949，黄金字节对拍测试） |

- **CBOR 就是库里的"第二个格式"**：二进制、定长、标准互操作；实测同一份数据 JSON 47 字节 / CBOR 25 字节。
- 现在的格局是**两个正交维度**：人类可读（JSON）+ 机器紧凑（CBOR）。这不是"只做了一种"，而是刻意做成"你要哪种都有标准答案"。
- 为什么看起来只有 JSON：汇总头 `eserde/eserde.hpp` 缺省只开 JSON（`ESERDE_ENABLE_CBOR` 默认 0），单格式头不 include 就一个字节都不占——这是设计（不替你决定），不是遗漏。

## 2. 为什么 YAML / XML 不在库内：三层原因

1. **架构不拦**：ADR 0001 明确否决"本体持格式白名单"（理由是"每加一个格式都要改本体，本体会变成所有人的公共瓶颈"）。格式是平级模块，谁写谁进，`field_key<T>(i, "格式名")` / `field_skipped` 已为任意格式就位。手册 3.8 用约 70 行示范了一个 TOML-ish 写端。
2. **规范复杂度**：YAML / XML 的完整读写是 5k～20k 行级别的工程（对照：json.hpp 含完整读写 + 转义 + 错误码才 925 行），而且在零第三方 / 零异常 / 零动态分配 / `-Os` 的约束下裁剪后依然大——这不是"加一个文件"的量级。
3. **语义摩擦**：两个格式的核心卖点（YAML 的隐式类型 / 锚点；XML 的属性通道 / 实体 / 命名空间）与 eserde 的模型——"字段类型由 C++ 类型决定，错了报 `type_mismatch`，失败不动原对象"——直接冲突，或需要为每个格式新设计一套映射策略。

## 3. YAML 的账本

### 3.1 规范与参考实现（量级参考，随版本浮动）

| 实现 | 语言 | 规模 |
|---|---|---|
| libyaml（YAML 1.1 事实标准） | C | ≈ 1.2 万行 |
| yaml-cpp | C++ | ≈ 2 万行 |
| **eserde::json（本仓库，写+读全功能）** | C++17 | **925 行** |

另：YAML 有 1.0 / 1.1 / 1.2 三版并存且行为有差异；**YAML 1.2 声明 JSON 是其语法子集**——现有的 JSON 解析器已经覆盖 YAML 的"JSON 形态"。

### 3.2 完整读端要处理的特性清单

缩进块、`|` / `>` 多行标量、`&锚点` / `*别名`（可构造共享引用甚至环）、`<<` 合并键、`!!tag`、隐式类型转换、引号省略、注释、流式 `[...]` / `{...}`、跨行键值拆分（`key:\n  - a`）。

### 3.3 与 eserde 模型的冲突点

1. **隐式类型 vs 严格类型**：`flag: yes` 读成布尔还是字符串由"内容长什么样"决定；eserde 的答案必须由 C++ 字段类型决定，错就报错。YAML 1.1 里 `yes/no/on/off` 是布尔、`0x1F` / `1e3` / 日期自动归类——这套"猜类型"与库的哲学正相反。
2. **锚点 / 环 vs 拷贝语义**：`read_from` 先解析到临时对象、全部成功才整体赋回；共享引用 / 环没有可拷贝的形状，要支持就得改读端语义或明确拒绝（拒绝本身又是一份文档 + 测试矩阵）。
3. **子集边界难画**：写端可以只写"严格带引号的字符串"，但那样 YAML 就没有卖点了；写宽松输出（`yes`、`1e3` 不带引号）又可能被标准工具按另一个版本误读（1.1 vs 1.2 的布尔 / 数字隐式转换不一致）。

### 3.4 工程量估算（估算值，非实测）

| 方向 | 估算 | 说明 |
|---|---|---|
| 写端（复用 `visit_fields`，缩进 + 引号策略） | 150～250 行 | 工作量小，但兼容性风险在"输出是否被标准工具正确读" |
| 读端（子集，不碰锚点 / tag / 隐式类型） | 600～1500 行起步 | 光"省略引号 + 注释 + 块缩进"的词法就比整个 JSON 读端复杂 |
| Flash 代价（`-Os`，整程序） | 写端 ≈ +2～4 KB；读端 ≈ +6～15 KB | 对照：json 全功能 +12.7 KB、cbor +8.7 KB（手册 3.9 实测） |

### 3.5 增量价值盘点

YAML 相对 JSON 对"设备配置"的增量 = **注释 + 省略引号 + 多行字符串 + 锚点复用**。其中"注释"用 JSONC 三十到六十行就能拿到（§5）；锚点在嵌入式配置里几乎用不上。

## 4. XML 的账本

### 4.1 规范与参考实现（量级参考，随版本浮动）

| 实现 | 语言 | 规模 / 体积 |
|---|---|---|
| expat | C | ≈ 2 万行 |
| pugixml（嵌入式最常用） | C++ | ≈ 1.7 万行，`-Os` 整编约 30～40 KB text 量级 |
| tinyxml2（功能裁剪版） | C++ | ≈ 6 千行——即便如此也远超 json.hpp |
| **eserde::json（本仓库）** | C++17 | **925 行 / +12.7 KB** |

语法特征比 JSON 多一个量级：prolog、DOCTYPE + 实体（**billion laughs 攻击面**）、CDATA、注释、处理指令、命名空间 / 前缀、5 个预定义字符实体 + 数字实体、属性 vs 子元素双取值通道、mixed content、空白策略、`<a/>` 自闭合。

### 4.2 与 eserde 模型的冲突点

1. **字段 ↔ 节点映射需要新策略**：同名重复子元素天然是数组（`<item>x</item><item>y</item>`），属性和子元素是两个取值通道——"字段名 → 键"的直接映射不成立。要认真支持 XML，先要设计并文档化"属性优先还是元素优先、重复元素怎么对应容器"的策略，这本身是一份文档 + 一套测试。
2. **命名空间**：前缀剥不剥？剥了与标准工具写出的文档脱节；不剥，字段名就带冒号，`[[efmt::arg(xml = "...")]]` 别名要写两套。
3. **实体展开的开与关**：不开 = 读不了带 DOCTYPE 的现实文档；开 = 引入 billion laughs（配置来自不可信来源时这是真实攻击面）。

### 4.3 收益侧最弱

- 设备配置场景 XML 几乎没有存在感——配置的世界是 INI / JSON / YAML / TOML。
- XML 的典型场景（SOAP、旧系统互操作、行业协议）要求的是**完整 XML**：半吊子子集接不上，而完整 XML 的成本就是 §4.1 那个量级。
- 与 JSON / CBOR 相比增量价值 ≈ 0：XML 既不更紧凑（标签重复、冗长），也不更易读（对人类比 JSON 差）。

## 5. 替代方案：按场景选，而不是按格式选

| 真实需求 | 推荐做法 | 成本 |
|---|---|---|
| 人要手写配置，想要注释 | **JSONC**（JSON 读端放开 `//`、`/* */`，可顺带放宽尾逗号） | 读端加 30～60 行；JSON5（单引号 / 无引号键 / 十六进制 / 多行字符串）约 200～400 行 |
| 输出给 PC 端标准工具消费（YAML / XML 的"只写"场景） | 自写**只写端子集**模块（手册 3.8 的套路，不动库） | 150～250 行 + 一组"标准工具能读"的兼容性测试 |
| 对接必须双向 XML 的旧系统 | 独立解析模块 + 明确子集边界文档（不塞进 eserde/ 当第一公民） | 量级见 §4.1，先跟对方确认"子集可接受"再动手 |
| 想要 TOML 风格 | 手册 3.8 已给可编译模板 | 约 70 行，已入库文档（`docs/libs/ESERDE-使用手册.md` 3.8） |

## 6. 结论与建议

1. **不内置完整 YAML / XML**：工程量高一个量级（5k～20k 行 vs 现有格式几百行），收益与 JSON / CBOR 重叠或与嵌入式场景无关，且与库的"严格类型 + 失败不动对象 + 子集边界明确"模型有真实摩擦。现有 81 checks 与文档都不必为此改动。
2. **架构零改动**：想要哪个格式都能按 3.8 套路自写成模块；真到"写端 + 读端"都验证过、确实有持续需求时，再按 json.hpp / cbor.hpp 的模式提一个 `eserde/yaml.hpp`（或 `json5.hpp`）单文件单开关进库——但那之前先回答三个问题：**谁生产、谁消费、能否接受子集**。
3. 若只是"想要注释"：**JSONC 是性价比之王**——三十到六十行的读端改动，不引入新格式，不破坏现有语义与测试。
